How this is scored



  A question is not scored pass-or-fail, and a model’s score is the mean of four areas rather
  than one pooled total.




  

    
The questions are real

    

      Every prompt is one a developer would type: “I stored a blob for 10 epochs and it
      expires next week. How do I extend it?” Answers come back as prose and code, the
      length of a real reply.
    

  

  

    
Expectations, written in advance

    

      169 expectations across 42 questions: the command to run, the call to make, the mistake to
      avoid. Each is prose, so a second model reads the answer and judges whether it is met.
    

  

  

    
Expectations are counted, not questions

    

      Four of five expectations right is not the same as none. Scored pass-or-fail, a model that
      gets most of every answer scores the same as one that gets none of it. Counting expectations
      tells them apart.
    

  

  

    
Four areas, equally weighted

    

      Fundamentals, storing, building and operating, averaged. Building holds 20 of the 42
      questions, so a pooled total would let it set the score and bury fundamentals’ 6.
    

  

  

    
Asked more than once

    

      The same model asked the same question twice does not always answer the same way. A run that
      asks more than once scores the average, and each card records how many attempts it used.
    

  

  

    
Every question points at a page

    

      Each question cites the documentation a correct answer comes from, so the suite measures
      whether Walrus is documented rather than what a model memorised. All 42 do, and an
      expectation its page does not support is a defect in the suite.
